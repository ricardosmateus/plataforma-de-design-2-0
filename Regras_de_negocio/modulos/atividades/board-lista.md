# Regras de Negócio — Quadro de Trabalho de uma Tarefa

> **Versão:** 1.41.0 · **Status:** Implementado · BOARD-PESQUISA-012 a 087 **construídas**
> **Conferido em:** 15/09/2026, contra `board.html`, `js/board.js`, `js/pesquisa.js`, `js/ia.js`, `api/src/rotas/pesquisa.ts`, `api/src/pesquisa/investigacao.ts` e `api/prisma/schema.prisma`
> **Módulo:** Atividades · **Página:** `board.html`
> **Gerado sob:** `Skills/regra_de_negocio.skill`
> **Documentos irmãos:** [`atividade-lista.md`](atividade-lista.md) — de onde vem a tarefa e quem pode mexer nela · [`board-analise-pre-implementacao.md`](board-analise-pre-implementacao.md) — o levantamento que precedeu estas regras · [`ideias-movimentacao.md`](../ideias/ideias-movimentacao.md) · [`ia-assistente-conversa.md`](../ia/ia-assistente-conversa.md)

Uma tarefa da atividade pode ter um espaço de trabalho próprio: um canvas onde a pessoa monta quadros de colunas e enche de registros. É isso que `board.html` é. Ela não substitui a lista de tarefas — ela é o *dentro* de uma tarefa.

---

## 1. Regras

### 1.1 Como se chega aqui — `BOARD-ACESSO`

| ID | Regra | Fonte |
|---|---|---|
| BOARD-ACESSO-001 | O campo **`tipo`** da tarefa decide **o que acontece** quando ela é acessada. Hoje os dois tipos abrem uma tela local (`pesquisa` → `board.html`, `matriz_csd` → `matriz_csd.html`); amanhã um tipo pode disparar uma ferramenta externa que traz o conteúdo pronto. Nunca se decide pelo texto do título. | Decisão A24, ampliada por A31 |
| BOARD-ACESSO-002 | **Toda tarefa tem um espaço de trabalho.** `tipo` é escolhido na criação e o padrão é **`pesquisa`** — inclusive para a tarefa-semente (`ATV-ACESSO-002`). Não existe tarefa sem destino. | Decisão A31 |
| BOARD-ACESSO-007 | O catálogo de tipos é **fechado no banco** e cresce por migração — nunca por texto livre. Um tipo cujo destino ainda não foi construído não mostra o botão "Acessar tarefa" (rede de segurança de A13), mas isso é estado de obra, não um tipo válido em produção. | Decisão A31 |
| BOARD-ACESSO-003 | `board.html` só abre com os **quatro ids** na URL (`empresa`, `projeto`, `ideia`, `tarefa`). Faltando qualquer um, é navegação inválida: volta para o lugar mais próximo que ainda faz sentido, não mostra estado vazio. | Decorre de IDEIA-ISO-002 |
| BOARD-ACESSO-004 | O painel da esquerda mostra o título, a descrição e o status **da tarefa de verdade**, lidos da API. | Decorre de ATV-ACESSO-005 |
| BOARD-ACESSO-005 | Tarefa concluída abre em **somente leitura** — sem criar, editar, mover ou excluir. O modo vem do `status` da tarefa, nunca de um parâmetro na URL. | Decisão A27 |
| BOARD-ACESSO-006 | São **dois caminhos** até a tela — o botão "Acessar tarefa" do card e o item "Acessar" do menu de três pontinhos — e os dois usam o **mesmo destino**, calculado uma vez por card. Nenhum dos dois decide para onde ir por conta própria. | Decorre de IDEIA-MOV-009 |

**Por que o `tipo` e não o título (BOARD-ACESSO-001).** O protótipo decidia o destino comparando o texto do título com `"Matriz CSD"`. É exatamente o defeito que `IDEIA-MOV-015` já teve que corrigir na ponte entre o quadro de idéias e a atividade, e quebra das mesmas três maneiras: dois títulos iguais, título editado depois, e nenhuma forma de uma tarefa nova declarar que tela ela quer. Um campo fechado no banco resolve os três.

**Por que `sem_tela` deixou de existir (BOARD-ACESSO-002).** A v1.0.0 tinha um terceiro tipo, `sem_tela`, para a tarefa que era só um item de lista — e ele era o padrão. Isso quebrou em uso real: toda tarefa criada antes da migração herdou `sem_tela`, ficou sem o botão "Acessar tarefa", e — como não existe rota para editar o tipo de uma tarefa — ficou **permanentemente sem como abrir**. Duas tarefas órfãs na mesma atividade.

A correção não foi mostrar o botão mesmo assim: foi remover o conceito. Toda tarefa tem onde trabalhar, e o tipo diz **que trabalho é**, não **se existe trabalho**. O padrão passou a ser `pesquisa` porque descobrir é o primeiro movimento de qualquer atividade — é o que a tarefa-semente faz por definição, copiando título e descrição da idéia.

**Por que o campo se chama `tipo` e não `tela` (BOARD-ACESSO-001).** Porque a tela é consequência, não a coisa. Hoje escolher "Pesquisa" abre um quadro em branco para a pessoa preencher; a intenção é que passe a disparar uma busca externa que devolve o quadro **já preenchido** com o que ela procurava. O nome do campo precisa sobreviver a essa mudança — e sobrevive, porque o que a pessoa escolhe é o tipo de trabalho, não o destino do clique.

**Por que os dois caminhos leem o mesmo valor (BOARD-ACESSO-006).** É `IDEIA-MOV-009` outra vez ("três gestos, uma porta"): dois caminhos para a mesma ação são duas chances de divergirem — alguém corrige o roteamento do botão e esquece do menu, e a tela passa a levar a lugares diferentes dependendo de onde se clicou. Era exatamente o estado anterior: o botão do card já roteava pelo `tipo`, enquanto o menu ainda comparava o título com "Matriz CSD" e, em qualquer outra tarefa, fechava sem fazer nada. O destino agora é calculado uma vez, gravado no card como `data-destino`, e lido pelos dois.

**Por que o modo leitura vem do status (BOARD-ACESSO-005).** Antes vinha de `?modo=leitura` na URL — quer dizer, de qualquer coisa que a pessoa digitasse na barra de endereço. Uma tarefa concluída abria editável se o parâmetro sumisse, e uma pendente abria travada se alguém colasse o link errado. O status está no banco; a query string é palpite.

### 1.2 O quadro — `BOARD-QUADRO`

| ID | Regra | Fonte |
|---|---|---|
| BOARD-QUADRO-001 | O quadro pertence à **tarefa**, não à atividade. Cada tarefa tem o seu; abrir outra tarefa mostra outro quadro. | Decisão A25 |
| BOARD-QUADRO-002 | No formato de post-its a estrutura é **quadro > coluna > registro**: um quadro tem N colunas; cada coluna tem N registros. O formato documento não tem colunas — ver BOARD-QUADRO-006. | Interface existente; ressalva acrescentada em 13/09/2026 |
| BOARD-QUADRO-003 | Título de **quadro** e de **coluna** podem ser vazios — é escolha de layout, e a interface já oferece "deixe em branco para uma coluna sem título". O título do **registro** não pode: um card sem texto é um card que ninguém sabe ler. | Interface existente |
| BOARD-QUADRO-004 | **A tela é sempre o canvas.** Não existe estado vazio de tela cheia: tarefa sem quadro mostra a mesma superfície de trabalho, com "Novo quadro" no rodapé. | Decisão A33 |
| BOARD-QUADRO-005 | Excluir a tarefa apaga o quadro dela junto. | Decorre de ATV-TAR-EXCLUI-001 |
| BOARD-QUADRO-006 | Existem **dois formatos de quadro**, no campo `tipo` (`postits`, padrão, e `documento`). O de post-its segue a estrutura de BOARD-QUADRO-002; o de documento **não tem colunas** — o texto inteiro é um registro, e as referências são um segundo registro com título fixo. | Registrado 13/09/2026, a partir do schema e de `lerDaTela()` |
| BOARD-QUADRO-007 | As referências de um quadro-documento são guardadas **separadas do texto**, nunca emendadas no fim dele. Emendar obrigaria a separá-las de novo por adivinhação ao reabrir. | Registrado 13/09/2026 |
| BOARD-QUADRO-008 | O editor de referências **não tira a lista do DOM** enquanto se edita: apenas a esconde. Um autosave disparado no meio da edição (a pesquisa termina, alguém arrasta um quadro) gravaria o quadro sem as referências — que é como um editor destes costuma apagar dado sem ninguém perceber. | Registrado 13/09/2026; decorre de BOARD-SALVA-002 |
| BOARD-QUADRO-009 | Quadros têm **ordem** dentro da tarefa, persistida em `quadros.ordem`. Arrastar um quadro pelo cabeçalho troca a ordem; excluir um faz os seguintes deslizarem para fechar o buraco. | Registrado 13/09/2026, a partir de `drag-drop-quadros.js` e `reorganizar-quadros.js` |
| BOARD-QUADRO-010 | Arrastar quadro respeita o **zoom do canvas** (o deslocamento é dividido pela escala real do stage) e só começa depois de um **limiar** de movimento — sem o primeiro o quadro foge do cursor, sem o segundo clicar no título ou abrir o menu sacode o quadro. | Registrado 13/09/2026 |
| BOARD-QUADRO-011 | Uma resposta de pesquisa é dividida em quadros por seção, com as referências associadas a cada uma, e o **formato de cada quadro é decidido pelo conteúdo** (documento ou post-its). | Registrado 13/09/2026, a partir de `resposta-para-quadros.js` |

**Por que o quadro é da tarefa (BOARD-QUADRO-001).** A alternativa — um quadro por atividade, compartilhado por todas as tarefas dela — era defensável: daria um espaço comum onde o trabalho de várias tarefas se encontra. Perdemos isso de propósito. A tela abre no contexto de **uma** tarefa e mostra o título dela no painel da esquerda; um quadro compartilhado faria duas tarefas diferentes mostrarem o mesmo conteúdo sob dois títulos diferentes, e ninguém saberia a qual das duas um registro pertence.

**Por que três tabelas e não um `Json` (BOARD-QUADRO-002).** Guardar o quadro inteiro como um documento seria menos código hoje. O registro, porém, é a unidade que a pessoa move, edita e um dia vai querer procurar entre tarefas — e nada disso se consulta dentro de um blob. O custo de normalizar agora é uma migração; o de desnormalizar depois é uma migração **mais** todo o código que aprendeu a ler o blob.

**Por que não existe tela de estado vazio (BOARD-QUADRO-004).** Havia uma: ilustração, título e um botão "Novo quadro", ocupando a tela inteira no lugar do canvas. Ela saiu por duas razões.

A primeira é que ela estava condenada. A direção do produto é que a tarefa **chegue com conteúdo** — criado por quem abriu, ou trazido por uma ferramenta externa a partir do `tipo` (§5). Uma tela cujo propósito é dizer "ainda não há nada aqui" desaparece junto com o problema que ela descreve; construir em cima dela é construir sobre algo que se sabe temporário.

A segunda é que ela atrapalhava agora. Para aparecer, escondia o canvas **e o painel do assistente** — exatamente no momento em que o assistente é mais útil, porque a pessoa ainda não sabe por onde começar. O convite custava o recurso que atenderia o convite.

O canvas vazio não é um erro a ser explicado: é uma mesa limpa, com as ferramentas à mão no rodapé.

### 1.3 Gravar — `BOARD-SALVA`

| ID | Regra | Fonte |
|---|---|---|
| BOARD-SALVA-001 | Cada gesto no canvas (criar quadro, criar/editar/excluir registro, arrastar entre colunas) **grava o quadro inteiro**. Não há botão "salvar". | Decisão A26 |
| BOARD-SALVA-002 | A fonte da verdade na hora de gravar é o **que está na tela**. Não existe um modelo paralelo em memória para sair de sincronia com o DOM. | Decisão A26 |
| BOARD-SALVA-003 | A resposta da gravação é o quadro **relido do banco**, e a tela redesenha a partir dela. Ids de registro não sobrevivem entre uma gravação e a seguinte — a tela nunca depende deles. | Decisão A26 |
| BOARD-SALVA-004 | Quem pode gravar no quadro são os mesmos três papéis que podem mexer nas tarefas (`ATV-TAR-CRIA-004`). | Decorre de ATV-TAR-CRIA-004 |
| BOARD-SALVA-005 | Um `404` ao gravar significa que a tarefa deixou de existir enquanto a pessoa trabalhava. A tela volta para a atividade em vez de insistir. | Decorre de IDEIA-MOV-013 |
| BOARD-SALVA-006 | **Nada é gravado antes de o quadro ter sido carregado com sucesso.** Enquanto a carga não termina — ou se ela falha —, a tela vazia significa "ainda não chegou", não "quadro vazio". | Decisão A30 |
| BOARD-SALVA-007 | **Montar não é gravar, e quem relata precisa saber a diferença.** Todo caminho que monta quadro e dispara gravação tem de **olhar no resultado** da gravação: desenhar na tela e falhar no `PUT` produz uma tela certa e um banco vazio, e a pessoa lê só a confirmação. Quando a gravação falha, isso é dito — sem desdizer o passo anterior, porque os quadros **estão** na tela. Autosave já em curso não é falha: o pedido entra na fila daquele (`BOARD-SALVA-002`) e não há nada a relatar. | Achado em uso real pelo Ricardo · corrigido 16/09/2026 |

**Por que um PUT do quadro inteiro (BOARD-SALVA-001).** A alternativa seria uma rota por gesto: criar coluna, renomear quadro, mover registro, excluir card. Duas coisas empurraram para o outro lado. A tela já salvava sozinha a cada gesto — o "Salvando..." do botão Voltar existia desde o protótipo, só que sem gravar nada —, então seriam doze rotas servindo a um único autosave. E arrastar um registro entre colunas muda **duas** colunas ao mesmo tempo: com estado inteiro isso é o caso comum, com rota por gesto é o caso especial que sempre esquece de ser tratado.

**Por que a trava de BOARD-SALVA-006 existe.** É o outro lado de `BOARD-SALVA-002`: se o que manda é o que está na tela, então uma tela que ainda não recebeu os dados manda uma lista vazia — e o PUT, que substitui tudo, apaga o quadro da pessoa. Não é hipótese: aconteceu em teste. A pessoa abriu a tela, a carga não tinha terminado, um autosave disparou e o quadro sumiu do banco. Por isso a regra não é "avisar" nem "tentar de novo": é **não gravar**, porque uma gravação errada aqui é destrutiva e silenciosa.

A trava não impede esvaziar um quadro de propósito — depois da carga, apagar o último card e gravar vazio é uma gravação legítima. Ela só separa "vazio porque a pessoa esvaziou" de "vazio porque nada chegou".

**O preço, declarado.** Duas pessoas no mesmo quadro ao mesmo tempo: a última gravação vence, sem aviso, e o trabalho da outra some. É a mesma troca que `ideias-movimentacao.md` §4 já aceitou para movimentação de idéias, pelo mesmo motivo (o volume de uso atual), e está registrada em §5 como pendência — não como detalhe resolvido.

### 1.4 A tarefa, vista daqui — `BOARD-TAREFA`

| ID | Regra | Fonte |
|---|---|---|
| BOARD-TAREFA-001 | Finalizar e reabrir a tarefa usam a **mesma rota** de `ATV-TAR-CONCLUIR`. Só mudam `status`. | Decorre de ATV-TAR-CONCLUIR-001 |
| BOARD-TAREFA-002 | Excluir a tarefa usa a **mesma rota** de `ATV-TAR-EXCLUI`, e leva de volta para a atividade. | Decorre de ATV-TAR-EXCLUI-001 |
| BOARD-TAREFA-003 | **Editar** título e descrição da tarefa **não acontece aqui** — acontece em `atividade.html`. | Decisão A28 |
| BOARD-TAREFA-004 | Concluir uma tarefa **não move a idéia** para "Finalizado" e **não tira a pessoa da tela**. Quem move a idéia é concluir a atividade inteira. | Decorre de IDEIA-MOV-014 |
| BOARD-TAREFA-005 | Voltar leva à **mesma atividade**, com empresa, projeto e idéia na URL. | Decorre de ATV-ACESSO-001 |

**Por que editar não acontece aqui (BOARD-TAREFA-003).** Duas telas gravando o mesmo campo é a receita de divergirem — é o mesmo raciocínio de `IDEIA-MOV-009` ("três gestos, uma porta"), aplicado a telas em vez de gestos. `atividade.html` já lista todas as tarefas e é o lugar natural para renomear uma. O botão que existia aqui, aliás, nunca gravou nada: reescrevia o texto na tela e pronto — e o backend não tem, até hoje, rota de edição de tarefa.

**O que BOARD-TAREFA-004 conserta.** O protótipo, ao concluir uma tarefa, gravava duas chaves de `localStorage`: `tarefa-1-status` (que só funcionava para uma tarefa fixa) e `idea-finalizada`, que criaria uma idéia **nova** direto na coluna "Finalizado" — contradizendo `IDEIA-CRIA-003` ("toda idéia nasce em Minhas idéias"). E redirecionava para fora. Concluir uma tarefa é um evento pequeno: não move idéia, não cria idéia, e não interrompe quem está trabalhando.

### 1.5 Registro vira tarefa — `BOARD-REGISTRO`

| ID | Regra | Fonte |
|---|---|---|
| BOARD-REGISTRO-001 | Um registro do quadro pode virar uma **tarefa da atividade**, pela mesma rota de `ATV-TAR-CRIA`: nasce no fim da lista, pendente e `pesquisa`. | Interface existente |

**Por que existia e não funcionava.** O menu do card já oferecia "Nova tarefa" desde o protótipo — gravava o registro em `localStorage` e navegava para a atividade. Quando `atividade.html` passou a usar a API, parou de ler essa chave, e o botão virou uma navegação que não criava nada. A ponte foi refeita pela rota real.

> **Nota de 13/09/2026.** O parágrafo abaixo descreve o estado de 29/08 e fica como registro do raciocínio da época. O que vale hoje está em §1.8.

**Por que desativado e não removido (BOARD-IA-001, histórico).** O que a tela fazia era encenação: o saldo "0 de 100" estava escrito no HTML, e clicar em "Pesquisar" sempre abria "Créditos insuficientes" — um modal sobre um sistema de créditos que não existe em lugar nenhum do produto. Isso depende da **decisão D2** (crédito por usuário ou por empresa), aberta desde o módulo de empresas e que bloqueia a publicação. Um botão desativado com explicação é honesto sobre o que ainda não existe; um botão que finge cobrar, não. Remover também seria defensável — ficou visível porque a pesquisa é o motivo pelo qual esta tela vai existir, e escondê-la faria a intenção do produto sumir do lugar onde ela deve estar.

### 1.7 Tarefa concluída não se mexe — `BOARD-LEITURA`

| ID | Regra | Fonte |
|---|---|---|
| BOARD-LEITURA-001 | Tarefa com status **concluída** abre em somente leitura. O quadro fica visível e legível; nada nele pode ser criado, movido, editado ou excluído. | Decisão A32 |
| BOARD-LEITURA-002 | Em somente leitura ficam indisponíveis: **arrastar registros**, editar título e descrição de registro, **"Novo registro"**, **"Novo quadro"**, os menus de card e de quadro (incluindo excluir) e a edição do título do quadro. | Decisão A32 |
| BOARD-LEITURA-003 | **"Pesquisar" fica desativado** numa tarefa concluída — pesquisar reescreveria o resultado que a conclusão congelou. Isso vale **independentemente** de `BOARD-IA-001`: se um dia a pesquisa for liberada, a tarefa concluída continua sem ela. | Decisão A32 |
| BOARD-LEITURA-004 | Em somente leitura **nada é gravado**: o autosave não dispara, nem para um gesto que tenha escapado de alguma trava. | Decisão A32 |
| BOARD-LEITURA-007 | **A trava de somente leitura mora em cada porta que cria conteúdo, não numa só.** Toda função que cria quadro ou card checa o modo **na própria entrada**. Guarda em uma irmã e não na outra é pior que guarda em nenhuma: a tela desenha o que o servidor vai recusar, a narração confirma o que não aconteceu, e o defeito só aparece na próxima visita — como o quadro em branco achado em 16/09/2026, em que `criarQuadroDocumento` não tinha a guarda que `criarQuadroResultado` já tinha. | Achado em uso real pelo Ricardo · corrigido 16/09/2026 |
| BOARD-LEITURA-005 | O único caminho para voltar a editar é **reabrir a tarefa** (`BOARD-TAREFA-001`). Reabrir devolve a tela ao estado editável na hora, sem recarregar. | Decisão A32 |
| BOARD-LEITURA-006 | O modo vem do **`status` da tarefa**, não de um parâmetro na URL. Ver `BOARD-ACESSO-005`. | Decisão A27 |

**Por que congelar, e não apenas avisar.** Concluir uma tarefa é a afirmação de que aquele trabalho chegou a um resultado. Se o quadro continuasse editável, "concluída" viraria só um rótulo — o resultado poderia mudar depois de dado como pronto, e ninguém saberia se o que está na tela é o que foi concluído ou o que alguém mexeu depois. Travar a edição faz o status significar algo verificável.

**Por que reabrir é a única saída (BOARD-LEITURA-005).** A alternativa seria deixar editar e mudar o status sozinho, ou pedir confirmação a cada gesto. As duas transformam uma decisão — "isto não está mais pronto" — em efeito colateral de um clique. Reabrir é explícito, é uma linha só de esforço, e deixa o estado da tarefa sempre igual ao que a pessoa declarou.

**Por que BOARD-LEITURA-003 não depende de BOARD-IA-001.** Hoje "Pesquisar" está desativado para todo mundo, aguardando a decisão D2 dos créditos — então a regra parece redundante. Ela existe para o dia em que D2 sair: quem for reativar o botão mexe em `BOARD-IA-001`, e sem esta regra separada a liberação vazaria para as tarefas concluídas sem ninguém notar. A trava está no código como uma desativação que **só desativa, nunca ativa**, exatamente para sobreviver a essa mudança.

### 1.8 A pesquisa — `BOARD-PESQUISA`

Substitui `BOARD-IA-001`, revogada. O painel vive em `js/pesquisa.js` e nas rotas `/pesquisa/sessoes*`; o planejamento está em `planejamento-pesquisa-concorrentes.md`, na raiz do repositório.

| ID | Regra | Fonte |
|---|---|---|
| BOARD-PESQUISA-001 | O botão "Pesquisar" do painel da tarefa **executa uma busca externa de verdade** e devolve o resultado como quadro. Não é mais encenação nem simulação. | Registrado 13/09/2026, a partir do código |
| BOARD-PESQUISA-002 | O painel de pesquisa **nunca desenha dentro de `#canvasStage`**. Um resultado que chega segundos depois, desenhado ali, viraria estado do quadro sem ninguém ter pedido — e `lerDaTela()` o gravaria (`BOARD-SALVA-002`), fazendo o quadro virar um segundo dono de um fato que `pesquisa_entidades` já guarda. Uma tarefa que já é uma pergunta inteira não tem três perguntas dentro — então o modelo preenchia a cota alargando o assunto. Cota de pergunta é cota de busca paga: o piso não só desviava, cobrava por isso. O piso virou 1.

A segunda estava na instrução: *"Nome próprio é sinal forte de fato externo — `Pesquisar outras logitechs` é pesquisa de concorrentes"*. Ela ensinava que empresa nomeada significa pesquisa de mercado. Mas o que faz "outras logitechs" pedir concorrentes é a palavra **outras**, não o nome próprio — e a instrução não dizia isso. Agora diz, com os dois exemplos lado a lado.

A terceira era a ficha da empresa. Ela entra no contexto para o planejador **interpretar** a tarefa, e estava sendo usada para **substituí-la**: os motivos que ele escreveu diziam, com todas as letras, *"complementa a pesquisa de concorrentes diretos da iHouseLog"*. Ninguém pediu concorrentes. A regra nova separa as duas coisas.

**E a garantia, porque instrução não basta.** `BOARD-PESQUISA-027`: quando a tarefa está escrita como pergunta, o servidor a põe como primeira do plano, tenha o modelo obedecido ou não. Mesma disciplina do teto de 3–6, que também é cortado no servidor: pedir é instrução, garantir é garantia — e o que está em jogo é a pessoa receber a resposta que pediu.

**O defeito de 14/09/2026, achado pelo Ricardo em uso real.** A investigação sobre a Loggi devolveu resposta certa para as quatro perguntas, com fonte — e o board mostrou outra coisa. O primeiro quadro tinha o título da pergunta 1 e, dentro, as respostas 1, 2 e 3 grudadas; e havia um post-it *"A Loggi opera serviço de ponto de coleta em condomínios residenciais ou comerciais? — Responda aqui…"*, como se ninguém tivesse respondido. A resposta estava logo abaixo da pergunta o tempo todo.

**A causa era um número.** `secoesDaResposta` só reconhecia cabeçalho de até **80 caracteres**. O limite fazia sentido para as formas ambíguas (negrito sozinho, frase capitalizada com dois-pontos), onde um teto baixo impede um parágrafo inteiro de virar título. Mas valia também para `# Assunto`, que é marcação inequívoca — a linha É um título, independente do tamanho.

Antes da Fase 1a isso nunca aparecia: ia uma pergunta ao provedor e a resposta raramente tinha cabeçalho longo. Depois da 1a vão de 3 a 6 perguntas, o provedor repete cada uma como cabeçalho, e **pergunta é longa**: duas das quatro passaram de 80 caracteres, não viraram título, caíram no corpo da seção anterior — e lá `partirSecao` as confundiu com perguntas que o provedor teria feito de volta.

**O que isso ensina sobre a Fase 1a.** Ela mudou a FORMA da resposta, não só o conteúdo, e um pedaço da máquina calibrado para a forma antiga continuou rodando com a régua velha. O corpus do roteador não pegaria isso, os testes puros não pegariam, e a prova com DOM da 1a usava uma resposta curta de uma pergunta só. Quem pegou foi o uso. Agora há `ferramentas/provar-quadros.mjs`, que trava o caso com a resposta real desta investigação.

**O defeito que a Fase 1b encontrou, e que ninguém tinha visto.** A persistência entrou no plano como "a narração sobrevive ao F5" — conforto. Lendo o código da 1a com cuidado apareceu coisa maior: **o servidor não para quando a aba fecha.** A busca completa, o crédito é consumido e a consulta é gravada; quem some é só o cliente — e é ele quem monta o quadro. Ou seja, fechar a aba no meio de uma investigação **custava o dinheiro de uma busca e não entregava nada**.

Pior: o texto da resposta nem estava guardado. `pesquisa_consultas` tinha pergunta, nível, resultado, provedor e fontes — tudo menos a prosa que se pagou para obter. Ela vivia no corpo HTTP e virava conteúdo do quadro que o navegador desenhava. Se o navegador não desenhasse, o texto não existia em lugar nenhum.

**Por que guardar a resposta não contraria BOARD-PESQUISA-002.** Aquela regra separa o CANVAS de `pesquisa_entidades`: dois donos do mesmo fato divergem em silêncio. Aqui os papéis também são distintos, e é justamente por isso que as duas cópias fazem sentido: a **consulta é o registro do que foi comprado**; o **quadro é o que a pessoa resolveu ficar**. Editar um card não reescreve a consulta — e é isso que torna possível conferir depois se o quadro ainda diz o que a busca disse.

**O que a Fase 1a trocou, e o que ela deliberadamente não trocou.** Trocou o portão: `SUJEITO_EXTERNO` e companhia deixaram de decidir se uma tarefa vira busca. `testes/roteador.test.ts` media a heurística em **14 de 18**, e os quatro erros eram a mesma falha quatro vezes — verbo de levantamento com alvo que é nome próprio ou categoria de produto, contra uma lista fechada de substantivos genéricos. Nenhuma lista fechada cobre nomes próprios, então aquilo não tinha conserto por ajuste: tinha por troca de mecanismo.

Não trocou a resolução de referência (`BOARD-PESQUISA-021`), nem a busca em si: continua sendo uma chamada ao provedor, que encadeia internamente. O que mudou é a **pergunta** que ela recebe — a tarefa mais as perguntas planejadas, em vez do texto cru. `web_fetch` por página e síntese com fonte por afirmação são Fase 1b.

**A estimativa virou portão (BOARD-PESQUISA-037).** Por um dia ela foi só informação: o evento `plano` entregava o custo em reais, com a comissão dentro, antes de a busca sair — e a busca saía sozinha logo depois. Estava dito aqui, em vez de escondido, mas dizer não conserta. Desde 14/09/2026 o stream de `investigar` **termina** no plano, e buscar é uma segunda chamada que só existe se alguém clicar.

**E o portão saiu do caminho um dia depois (BOARD-PESQUISA-037, revista).** Instrução do Ricardo, 15/09/2026: *"ele já clicou, e já sabemos que ele quer pesquisar"*. O portão tinha sido construído para segurar uma coisa — gastar sem ninguém autorizar — e a autorização já existia um passo antes, no clique em "Pesquisar". Pior: a única informação que o portão carregava era o preço, e o preço tinha saído dali horas antes, quando os valores foram recolhidos para Configurações. Sobrou uma pergunta sem conteúdo, feita a quem já tinha respondido.

**O quadro em branco, e por que ele passou por todas as provas (BOARD-LEITURA-007, BOARD-SALVA-007).** Achado em uso real pelo Ricardo: uma pesquisa concluída, salva, e na volta o board vazio. Duas causas, uma em cima da outra. A primeira: `criarQuadroDocumento` não tinha o `if (modoLeitura) return null` que `criarQuadroResultado` já tinha — a guarda estava numa irmã e não na outra. A segunda, que é o que tornou a primeira invisível: a narração dizia *"Montei 3 quadros no board"* e disparava a gravação **sem olhar no que dava**. Os quadros estavam na tela, a gravação era recusada em silêncio, e a única coisa que a pessoa tinha lido era uma confirmação.

**Por que nenhuma prova pegou isso antes.** Todas as suítes existentes substituíam `criarQuadroResultado` e `criarQuadroDocumento` por dublês — cada uma provava o que vinha *antes* de montar o quadro. Nada cobria o trecho board → `lerDaTela()` → `PUT` → recarregar, que é exatamente onde os dois defeitos moravam. A prova nova (`ferramentas/provar-gravacao.mjs`) carrega a página inteira e só finge a rede; foi conferida falhando sem as correções. É a lição mais cara desta correção: um dublê bem colocado apaga justamente a fronteira onde o defeito mora.

**Os três lugares que mostravam o mesmo dinheiro (BOARD-PESQUISA-018a).** Antes de 15/09/2026 o valor aparecia em três momentos da mesma jornada: o teto em cima do botão de buscar, o custo no fim de cada resposta do caderno, e o custo no rodapé do relatório. Três números, uma decisão — e a decisão já tinha sido tomada quando o primeiro deles aparecia. Nenhum foi substituído por outro: os três saíram, e o valor passou a morar num lugar só, Configurações → Créditos de uso → Histórico de uso (`DIN-013`).

**Por que o preço antes de gastar não era a proteção que parecia.** Ele nasceu como proteção, e a intenção era boa: ninguém deve gastar sem saber quanto. Mas o teto aparecia **depois** do clique em "Pesquisar" — depois da decisão, portanto —, e ainda por cima como um valor que quase nunca acontece. Custava atenção, criava expectativa errada e não mudava nada. O que protege o gasto continua no servidor: o **teto por investigação** e a reserva de `018`. Tirar o número da tela não tirou nada da razão — a medição é a mesma (`DIN-011`), e é ela que alimenta o Histórico de uso.

**O que NÃO saiu, e por quê.** A tentação era apagar de `037` a `041` de uma vez, já que "o portão acabou". Seria trocar uma segunda pergunta por três buracos. `038`, `040` e `041` não descrevem a pergunta — descrevem o que o **servidor** faz com a espera que ele grava de qualquer jeito: sobreviver a fechar a aba, não buscar duas vezes com clique duplo, e devolver à espera quem ficou sem saldo. Nada disso deixou de ser verdade, e nada disso seria reconstruído por quem lesse um documento onde essas linhas não existem mais. Por isso ficaram, e ganharam `037a` dizendo em voz alta que o portão continua de pé do lado de lá.

**O laço que a remoção quase criou (BOARD-PESQUISA-086).** Tirar o portão significa: chegou `aguardando`, confirme. Só que o servidor manda `aguardando` em mais de uma situação — entre elas a de `039`, preço que subiu entre planejar e confirmar. Um cliente que confirma todo `aguardando` responderia a esse também, e o servidor responderia com outro, e cada volta é uma **busca paga**. A trava não é um contador de tentativas: é um parâmetro que só o stream de planejamento recebe. O caminho de `/buscar` não tem como se auto-confirmar porque nunca ganha a permissão, e não porque alguém lembrou de contar até dois.

**Por que ainda existe um botão de continuar (BOARD-PESQUISA-087).** Parece contradição com "o portão saiu", e não é: o que saiu foi perguntar de novo a quem **acabou de clicar**. Quem reabre a tarefa amanhã e encontra um plano parado não clicou em nada hoje — buscar por conta própria ali seria gastar o dinheiro de alguém a partir de um clique de ontem. É um botão só, e não um par: "agora não" é fechar a aba, e o plano fica guardado de qualquer jeito.

**Dois gestos, e eles pedem coisas diferentes.** O portão pergunta *"posso gastar?"* antes da busca; o rascunho (`BOARD-PESQUISA-033`) pergunta *"o que fica?"* depois dela. Foi tentador tratar o rascunho como o portão do gasto — ele já era uma decisão da pessoa, e adiar o portão teria sido barato. Mas no rascunho o dinheiro **já saiu**: decidir ali é escolher o que fazer com o que se pagou, não se paga. São duas perguntas, e uma não responde a outra.

**E os dois gestos caíram, com 24 horas de diferença e por motivos opostos.** O portão saiu porque **repetia** uma pergunta já respondida (o clique em "Pesquisar"). O rascunho saiu porque fazia uma pergunta **cedo demais**: pedia para escolher o que fica olhando uma lista dentro de um dialog, quando o lugar onde se julga se uma frase presta é o board, com ela ao lado das outras. O parágrafo acima continua certo no que afirma — as duas perguntas são diferentes, e uma não responde a outra —, e errado no que supõe: que as duas precisavam ser feitas *ali*.

**O que uma curadoria obrigatória custava, e não estava escrito em lugar nenhum.** Entre a busca terminar e o resultado aparecer onde serve havia um dialog que só podia ser atravessado decidindo. Quem só queria ver o que tinha comprado precisava primeiro curar. E a decisão era pedida no pior momento possível para tomá-la: antes de ver as frases no board, ao lado do que já estava lá — que é exatamente a comparação que faz alguém perceber que uma frase é redundante ou fraca.

**Por que `agruparEmSecoes` e `remontar` ficaram (BOARD-PESQUISA-035a).** Elas nasceram para o rascunho, e a leitura apressada é que morreram com ele. Não morreram: as investigações curadas entre 14 e 15/09/2026 têm `removida_pelo_usuario` gravado por afirmação, e reabrir uma delas tem de devolver ao quadro **o que aquela pessoa manteve — nem mais, nem menos**. Apagá-las por serem "código do rascunho" mataria a decisão de quem leu junto com a tela que a coletou. O padrão que elas aplicam, esse sim mudou: sem decisão gravada, tudo fica.

**Por que o preço mudou de lugar na tela.** Ele saía como mais um passo da narração, no meio da lista do que o assistente estava fazendo. Agora sai **colado no botão**, com peso de texto e não de legenda. Número numa linha e escolha em outra vira aviso; número em cima do botão vira decisão — e é a mesma razão pela qual "Agora não" não tem o peso visual de "Buscar agora": duas ações com o mesmo peso deixam a escolha sem recomendação, e a recomendação aqui é que ninguém gaste por inércia.

**O terceiro defeito achado em uso real, e o mais caro (14/09/2026).** Uma tarefa cuja descrição era literalmente `"Responda aqui..."` — o convite que o próprio produto escreve nos post-its de pergunta em aberto — virou **duas** investigações pagas, R$ 0,67. O planejador não recusou. Sem tarefa em que se apoiar, ele preencheu o vazio com a **ficha da empresa** e escreveu cinco perguntas sobre o mercado de lockers em condomínios. Os "porquês" que ele gravou denunciam o mecanismo: *"A proposta central da iHouseLog é…"*, *"A descrição menciona…"*. Ele planejou a partir do CONTEXTO, que é exatamente o que a regra 5 do prompt proíbe.

**Por que a regra 5 não segurou, e por que o conserto não foi no prompt.** A regra diz que a ficha da empresa nunca substitui a tarefa — e ela vale quando existe uma tarefa para não ser substituída. Aqui não existia. Pior: a regra 7 empurra na direção errada nesse caso (*"na dúvida, prefira perguntar"*). Mexer no prompt seria pedir ao modelo que reconhecesse um texto que qualquer comparação de string reconhece de graça — e **instrução não é garantia**, pela quarta vez neste projeto. A guarda virou `tarefaSemConteudo`, pura e testada, antes de qualquer reserva.

**Uma lição sobre a própria guarda.** A primeira versão escrevia a lista de placeholders já normalizada à mão, e errou na estreia: o aviso de falha do board termina em ponto, e a comparação passava ao lado por causa dele. A lista passou a ser normalizada pela **mesma função** que normaliza a entrada. Duas normalizações do mesmo dado é o defeito de sempre, em miniatura — e foi o teste que pegou.

**O que a documentação confirmou, e o que ela obrigou a consertar antes (15/09/2026).** A filtragem dinâmica existe de `web_search_20260209` em diante, **não cobra** pela execução de código que a realiza, e **preserva as citações** — `url`, `título` e `cited_text` continuam presos aos blocos de texto, então a fonte por afirmação (`031`) sobrevive. Três fatos que não dava para supor, e que mudaram o trabalho: o item deixou de ser "ligar a filtragem" e passou a ser "garantir que ligar não quebre nada".

**O que ela quebraria.** O corte entre preparação e resposta procurava `web_search_tool_result` **no nível de cima** do `content[]`. Com filtragem, os resultados chegam aninhados dentro do bloco de execução de código: a varredura acharia `-1` e devolveria a resposta inteira, com o *"Vou buscar informações sobre…"* colado na frente. Nenhuma linha do corte teria mudado — só a forma da resposta.

**E o teto de profundidade quase repetiu o erro em miniatura.** A primeira versão parava em 4 níveis, e **cada array come um nível**: o caminho documentado já gasta cinco. Um teto justo demais não falha com erro — ele silenciosamente para de achar o resultado, que é exatamente o defeito que se queria evitar. Foi o teste que mostrou, com um nível a mais do que a API documenta hoje.

**A síntese rodava no modelo mais barato — descoberto em 15/09/2026, lendo o `.env`.** `IA_MODELO=claude-haiku-4-5`, e tanto o planejador quanto a busca liam essa variável. O plano sempre supôs o contrário (*"barato para planejar, principal para sintetizar"*), e a tabela de custo dele — ~R$ 1,25 por investigação — foi calculada com Sonnet na síntese. O que estava em produção custava metade disso e pensava com metade da capacidade, na etapa que mais precisa dela.

**Por que separar e não trocar.** Trocar é decisão de dinheiro do usuário, e o ganho de qualidade não foi medido. O código passou a permitir a escolha, com o padrão igual ao de hoje: quem decide é quem paga, e a decisão custa uma linha no `.env`. É o oposto de embutir a preferência de quem escreveu o código.

**A porta estreita que a separação abriu, e que já estava aberta.** Modelo fora da tabela de preços fazia a investigação correr **de graça**: `tetoBuscaUsdMicros` devolve `null`, `null` virava estimativa 0, estimativa 0 não reserva nada, e no fim `custoDe` também devolve `null` — nem o consumo era lançado. As buscas encadeadas iam junto. O buraco existia antes; um `IA_MODELO_BUSCA` com erro de digitação só tornou fácil cair nele. Agora a investigação recusa.

**O que a régua achou na primeira rodada real (15/09/2026), e o que isso ensina sobre réguas.** Cinco de cinco casos passaram — e um deles passou **com uma duplicata na tela**: duas perguntas para a mesma coisa, uma busca paga a mais. A régua não olhava para duplicata, e *o que a régua não olha não existe*. O critério entrou, e o primeiro teste dele é o plano real que tinha passado.

**A causa era minha, e era assimetria.** `ehAMesmaPergunta(a, b)` divide as palavras comuns pelo tamanho de `a` — assimétrica de propósito. A garantia de fidelidade só perguntava `ehAMesmaPergunta(tarefa, p)`, a direção em que a tarefa longa quase nunca bate. Numa tarefa composta (*"quais marcas vendem no Brasil **e** qual a participação da Logitech?"*) com metade já validada no Bloco A, o modelo **acertou** — perguntou só o que faltava — e a garantia reinjetou a tarefa inteira por cima. A garantia que consertou um defeito criou outro, menor, no caso em que o modelo estava certo.

**O sinal que faltava no diagnóstico.** Descobrir se a pergunta duplicada veio do modelo ou da injeção exigiu calcular `ehAMesmaPergunta` à mão. O `porque` de cada pergunta já dizia isso — a injeção assina *"É a própria tarefa, escrita como pergunta"* — e o runner não o imprimia. Agora imprime: **um diagnóstico que existe no dado e não aparece na ferramenta custa uma investigação inteira para ser refeito.**

**O ponto cego do `tsc`, achado em 14/09/2026.** O `tsconfig.json` incluía só `src/` e `testes/`. Os scripts da raiz — `ver-investigacao.ts`, `medir-planejador.ts` — **nunca foram compilados**, e um deles foi estendido nesse mesmo dia sob três declarações de "tsc limpo" que não o tinham olhado. Ferramenta de diagnóstico que não compila quebra exatamente na hora em que alguém foi conferir um defeito. O `include` passou a cobrir a raiz e o `corpus/`.

**Por que a lacuna é apurada pela seção, e não pela pergunta do plano.** Seria mais bonito dizer *"a pergunta 3 ficou sem resposta"*. Mas o provedor parafraseia o cabeçalho: no dado real de 14/09/2026 a pergunta era *"Quais são as principais empresas de logtech que atuam no Brasil atualmente?"* e o cabeçalho virou *"1. Principais empresas de logtech que atuam no Brasil"*. Casar os dois exigiria comparação difusa, que erra em silêncio. A seção é o que existe de verdade no texto, e o cabeçalho dela **é** a pergunta, na prática.

**O terceiro defeito posicional do mesmo dia, e o mais bem escondido.** A lista que o rascunho devolve ao relatório e às lacunas não carregava o `inicio` de cada afirmação. `undefined >= 0` é **falso**, então `agruparEmSecoes` jogava tudo na primeira seção — e o resultado parecia plausível: a contagem saía "3 de 4" em vez de "2 de 4", com nomes de seções reais. Só a prova pegou. A correção foi fazer a **posição viajar com o item**, como o id já viajava: é a terceira vez que uma posição perdida produz erro silencioso (`BOARD-PESQUISA-031`, `remontar`, e agora esta), e as três tinham a mesma forma — um dado derivado do texto original sendo lido contra um texto diferente.

**O custo entra no relatório porque uma conclusão sem preço não deixa ninguém julgar se valeu.** É o total que saiu do saldo, com a comissão dentro e sem desmembrar (`DIN-007`) — o mesmo número da tela, agora no documento que vai circular. Sem ele, o relatório responde "o que descobrimos" e não responde "quanto custou descobrir", que é metade da decisão de repetir a investigação ou não.

**A tela de fontes não tem rota (BOARD-PESQUISA-053).** Ela se monta com o que o cliente já tem: `fontes` e `afirmacoes`, que chegam iguais no fim de uma busca e na recuperação de uma investigação antiga. Um endpoint novo seria uma segunda maneira de perguntar a mesma coisa, e duas maneiras divergem no primeiro ajuste. É a mesma economia de `afirmacoesDosBlocos`, que derivou a fonte por afirmação das citações que já vinham, em vez de pagar uma segunda leitura para descobri-la.

**O caderno é o contrário do assistente, e é por isso que ele é útil (BOARD-PESQUISA-047).** O assistente do projeto lê o conhecimento interno e responde com o que sabe. O caderno tem um material fechado na frente e não pode sair dele. Isso parece uma limitação e é o valor: toda frase da resposta aponta para uma fonte listada logo acima, e quando o material não responde, a resposta é dizer isso. É a régua do NotebookLM, e é ela que torna a resposta conferível por quem vai decidir dinheiro em cima dela.

**Instrução não é garantia — de novo.** O plano descrevia "responder só com as fontes já coletadas" como comportamento a pedir ao modelo. Pedir é frágil: um modelo que decide buscar transformaria uma pergunta de centavos numa busca cara, e por fora do portão. A chamada é feita **sem `tools`**: não há como buscar, tenha o modelo entendido a regra ou não. Mesmo princípio de `comPerguntaDaTarefa` no planejador — pedir é instrução, cortar é garantia.

**O material vai numa mensagem, não no `system`.** `system` é onde mora a instrução; misturar as duas coisas é o que faz um texto vindo da web parecer ordem. É o mesmo cuidado que já separa o contexto interno (no `system`) do conteúdo lido na busca (resultado de ferramenta) — e aqui ele importa mais, porque o material do caderno é, por definição, texto que veio da internet.

**Por que as afirmações viraram tabela, e não mais um campo Json (BOARD-PESQUISA-042).** `plano` e `passos` são Json porque ninguém os edita: são registro do que aconteceu, e o formato ainda ia mudar. A afirmação é o contrário. `removida_pelo_usuario` é um campo que **a pessoa muda**, e mudar um item dentro de um array Json é reescrever o array inteiro — foi exatamente isso que obrigou `anotarPasso` a serializar gravações numa fila. E a Fase 3 quer perguntar *"quais afirmações dependem desta fonte"*, que é pergunta de tabela. O caminho Json → tabela existe; o contrário não.

**O índice de array não sobrevive a ser gravado.** Ao vivo, `fonteIds: [0, 1]` são posições dentro da lista de fontes de uma resposta HTTP, e funcionam porque as duas pontas leem o mesmo objeto. Gravado, isso é uma referência que não referencia nada: basta a ordem mudar para a procedência apontar para a página errada — e o erro seria silencioso, que é o pior tipo num produto cujo valor é a fonte estar certa (`PES-006`). No banco a ligação é chave estrangeira; a API continua devolvendo índice, calculado contra a mesma lista que ela mesma entrega.

**O que a espera de `BOARD-PESQUISA-032` comprou.** Em 14/09 de manhã a decisão foi **não** gravar meio contrato — guardar as afirmações sem `removida_pelo_usuario` custaria uma migração que a Fase 2 substituiria. À tarde, com a forma do rascunho já provada em uso, o contrato foi guardado inteiro numa migração só. A regra que fica: adiar persistência de formato que ainda vai mudar é economia real, desde que o adiamento esteja escrito e tenha prazo — o prazo aqui era "quando a Fase 2 desenhar o rascunho".

**O defeito que isto fechou, e que ninguém tinha visto.** Antes, quem recarregava a página depois de uma investigação recebia a prosa e **todas as fontes empilhadas no primeiro quadro** — a recuperação não tinha como saber onde cada fonte entrava, porque essa informação (a posição de cada citação) só existia na resposta ao vivo. Com as posições gravadas, o resultado recuperado nasce igual ao resultado ao vivo. E `remontar` recalcula as posições sobre o que **sobrou**: sem isso, apagar uma afirmação no começo do texto empurraria todas as fontes seguintes para o quadro errado.

**`aguardando` não é `parada`.** Na narração são estados diferentes, com desenho diferente (✋ contra ⏸️), porque significam coisas opostas: `parada` é o assistente dizendo que não dá para seguir; `aguardando` é ele esperando você. Só uma das duas tem dinheiro do outro lado do botão. O relógio para junto, e é certo que pare: o tempo que a pessoa leva para decidir não é tempo de investigação.

**Duas etapas, dois lançamentos.** Planejar e buscar são chamadas separadas, cada uma com seu `operacaoId`, reserva e consumo. O planejamento **é cobrado mesmo quando decide não buscar** — o modelo rodou e o provedor cobrou de nós. Ele entra na razão como `nivel: conhecimento`, que o enum define literalmente como "não sai chamada para fora": o planejador raciocina, não busca.

**Como BOARD-PESQUISA-012 foi cumprida, e o que ela custou de verdade.** Quase nada de mecanismo: o servidor aceitava `nivelConfirmado` desde 02/09 e ninguém nunca mandou — o cliente parava em `planejar` e jamais chegava ao `409` de `consultar` (limite L3 do plano). O trabalho foi decidir **o que oferecer**, e isso virou `api/src/pesquisa/saidas.ts`, com `testes/saidas.test.ts` provando as duas metades da regra: toda recusa oferece caminho, e **nenhum caminho oferecido leva a outra recusa** — a armadilha seria mostrar "Buscar por proximidade" numa instalação sem provedor de lugares, transformando uma recusa em duas.

**O texto que precisou sair.** A recusa de `conhecimento` dizia *"Reescreva a tarefa como uma pergunta verificável (com número, data, nome ou fonte) e a busca executa."* Era a tela pedindo que a pessoa compensasse um limite nosso — e, no caso que originou tudo isto, a tarefa **já tinha nome próprio**: "Pesquisar outras logitechs que atuam aqui no brasil". O novo texto admite a falha: *"Li esta tarefa como reflexão... Posso estar errado — a leitura é por palavra-chave, e nome próprio costuma escapar dela."* Sem essa admissão, o botão ao lado leria como teimosia; com ela, é uma oferta.

**Um lugar só para o texto.** As recusas eram redigidas em dois lugares — as mensagens de `501`/`503` em `rotas/pesquisa.ts` e `motivoNaoExecutavel()` em `js/pesquisa.js` —, escritas em momentos diferentes e já divergindo; qual delas a pessoa lia dependia do caminho por onde ela chegou. Agora `planejar` devolve `impedimento` e `saidas`, e a tela desenha sem redigir. Junto saiu uma mentira pequena: confirmar `conhecimento` caía no `503` *"a pesquisa não está configurada"* — não falta configuração nenhuma, falta ser uma coisa que a plataforma faz (`PES-006`).

**Por que o feedback vai para o assistente, e não para o botão (BOARD-PESQUISA-016).** Porque o rodapé do compositor não comporta o que se quer contar. Ali cabe uma linha, sem histórico, apagada no fim — e a investigação da Fase 1 tem seis etapas para relatar. O painel certo já está na tela e já é o mesmo módulo (`BOARD-IA-002`): faltava a investigação ter direito de escrever nele. O ganho não é só a espera parecer menos morta; é a investigação passar a deixar **rastro** de onde ela leu e quanto custou, no mesmo lugar onde a pessoa vai fazer a pergunta seguinte.

**O que BOARD-PESQUISA-017 impede.** O caminho fácil seria a narração ser mensagem do assistente — a thread já sabe desenhar mensagem. Só que mensagem vai ao modelo na pergunta seguinte (`IA-CONV-004`), e aí toda conversa do projeto passaria a carregar "buscando 2 de 4" como se alguém tivesse dito aquilo. Ver `IA-CONV-NARRA-003`.

**Por que a estimativa é um número só (BOARD-PESQUISA-018).** Porque é o número que a pessoa precisa para decidir: o que vai sair do saldo dela. Mostrar "provedor R$ 0,95 + plataforma R$ 0,05" responde uma pergunta que ninguém fez e convida à que não interessa — comparar o nosso preço com a tabela do fornecedor a cada investigação. O desmembramento existe e continua existindo, em `consumos_pesquisa`, para auditoria nossa (`DIN-005`); o que `DIN-007` fixa é que ele não atravessa a fronteira da API.

**Como BOARD-PESQUISA-009 foi cumprida.** A regra foi escrita em 13/09 como não cumprida e implementada no mesmo dia. O encanamento já existia inteiro e desligado: `OperacaoConsumo` tinha `'pesquisa'`, `ORIGEM.pesquisa` apontava para a origem própria que DIN-005 exige, a descrição "pesquisa de concorrentes" estava escrita, e a tabela `consumos_pesquisa` existia com as colunas certas. Faltava a rota chamar. Ver `creditos-pagamentos-regras.md` para o que ainda não entra na conta.

## 2. Contrato da API

Todas autenticadas pelo cookie de acesso, e todas sob a corrente completa: **empresa → projeto → idéia → tarefa**. Qualquer elo que falhe devolve `404` com a mesma mensagem, pelo mesmo motivo de `IDEIA-ISO-004`: não contar a quem está adivinhando ids se a coisa não existe ou só não é dele.

### `GET /empresas/:empresaId/projetos/:projetoId/ideias/:ideiaId/tarefas/:tarefaId/quadros`

Devolve `{ quadros: [...] }`, cada quadro com suas colunas e cada coluna com seus registros, em ordem. **Lista vazia é resposta válida** e significa "tarefa sem quadro ainda".

Diferente de `GET .../tarefas`, aqui **não** existe "encontra ou cria": um quadro-semente seria conteúdo que ninguém pediu.

### `PUT /empresas/:empresaId/projetos/:projetoId/ideias/:ideiaId/tarefas/:tarefaId/quadros`

**Corpo:** `{ quadros: [ { titulo, colunas: [ { titulo, registros: [ { titulo, descricao } ] } ] } ] }`

Substitui o quadro inteiro da tarefa, numa transação. Devolve o quadro relido do banco.

| Situação | Resposta | O que a tela faz |
|---|---|---|
| Sucesso | `200` com `{ quadros }` | Redesenha a partir da resposta |
| Registro sem título, ou campo acima do limite | `400` com `campo` | Mostra o erro; o canvas continua como está |
| Sessão inválida | `401` | Renovação silenciosa; só então login |
| Papel não permite escrever | `403` | Mostra o erro |
| Qualquer elo da corrente falha | `404` | Volta para a atividade (BOARD-SALVA-005) |

Tetos: 40 quadros por tarefa, 12 colunas por quadro, 200 registros por coluna. Existem para recusar um payload absurdo antes de virar transação — não porque alguém vá esbarrar neles.

### Referências — `BOARD-REF`

Base: `/empresas/:empresaId/projetos/:projetoId/ideias/:ideiaId/tarefas/:tarefaId/referencias`. Mesma corrente de isolamento dos quadros (`abrirContexto` de `rotas/board.ts`).

- `GET` → `{ referencias: [{ id, tipo: "site" | "documento" | "imagem", url, nome, criado_em }] }`, mais antigas primeiro.
- `POST` com `{ url, nome? }` → `201 { referencia }`. `400` com `campo: "url"` para endereço inválido.
- `POST /imagem`, multipart com `nome?` e `imagem` → `201 { referencia }`. `400` com `campo: "imagem"` para formato, tamanho ou armazenamento indisponível; `502` se o bucket falhar.
- `POST /documento`, multipart com `nome?` e `documento` → `201 { referencia }`. `400` com `campo: "documento"` para formato, tamanho ou armazenamento indisponível; `502` se o bucket falhar.
- `POST /buscar` → `200 { referencias: [...só as novas], resumo: { concorrentes, sites, imagens, documentos }, avisos }`. `402` sem saldo, `503` sem busca configurada (`BOARD-REF-010`).
- `DELETE /:referenciaId` → `204`.
- Escritas: `403` sem papel de escrita, `409` para tarefa concluída, de outro tipo, ou no teto de 60.

### Rotas reaproveitadas

Nenhuma rota nova para o ciclo de vida da tarefa. `board.html` chama exatamente as mesmas de `atividade.html`:

- `PATCH .../tarefas/:tarefaId/status` — finalizar e reabrir (`ATV-TAR-CONCLUIR`)
- `DELETE .../tarefas/:tarefaId` — excluir (`ATV-TAR-EXCLUI`)
- `POST .../tarefas` — registro vira tarefa (`ATV-TAR-CRIA`)

## 3. Modelo de dados

```
tarefas
  ...                                             -- já existia
  tipo   TipoTarefa NOT NULL DEFAULT 'pesquisa'   -- BOARD-ACESSO-001/002
         -- enum: 'pesquisa' | 'matriz_csd'  (A31 retirou 'sem_tela')

quadros
  id            uuid (pk)
  tarefa_id     uuid (fk -> tarefas.id, CASCADE)
  titulo        varchar(60) NOT NULL DEFAULT ''   -- vazio é válido
  ordem         integer
  criado_em     timestamp
  atualizado_em timestamp

quadro_colunas
  id        uuid (pk)
  quadro_id uuid (fk -> quadros.id, CASCADE)
  titulo    varchar(60) NOT NULL DEFAULT ''       -- vazio é válido
  ordem     integer

registros
  id            uuid (pk)
  coluna_id     uuid (fk -> quadro_colunas.id, CASCADE)
  titulo        varchar(60) NOT NULL              -- CHECK: não vazio
  descricao     varchar(280) NOT NULL DEFAULT ''
  ordem         integer
  criado_em     timestamp
  atualizado_em timestamp
```

**Sobre o `CASCADE`.** Em `tarefas` o cascade é rede de segurança — na prática idéias são arquivadas, não apagadas. Aqui ele é **real**: `ATV-TAR-EXCLUI-001` apaga a linha da tarefa de verdade, e o quadro dela precisa ir junto. Um quadro órfão não teria como ser alcançado nem apagado por ninguém depois.
